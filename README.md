# FICC Bloomberg Chat Quote Parser

This project parses Bloomberg chat/email text into one quote record per bond quote.

PostgreSQL is the default production output. JSON, XLSX, paragraph JSON, and quote-line files remain available as debug outputs.

Splitting is two-step: local code first splits Bloomberg text into raw timestamped messages, then an OpenAI-compatible LLM classifies each raw message and identifies quote line ranges. The extractor LLM then extracts structured fields from those quote lines only.

## Setup

```bash
pip install -r requirements.txt
cp .env.example .env
```

Fill `.env` with OpenAI-compatible API and SQL Server credentials.

Initialize the PostgreSQL quote schema after setting `POSTGRES_PASSWORD`:

```bash
python -m ficc_bbg_parser.pg_schema
```

Install the frontend dependencies separately:

```bash
cd front
npm ci
cd ..
```

The frontend requires Node.js 20 or newer for development and builds. `npm ci` installs the exact dependency versions recorded in `front/package-lock.json`.

## Run

The default output mode is `postgres`:

```bash
python -m ficc_bbg_parser.cli \
  /path/to/pasted-text.txt \
  --input-source txt \
  --source-date 2026-06-04 \
  --stage all
```

This writes one transaction to `ficc.ingestion_run`, `chat_email`, `chat_paragraph`, `quote_line`, and `bond_quote`.

Use `--output-mode debug` to skip PostgreSQL and write only:

- `output/quotes.json`
- `output/quotes.xlsx`
- `output/extraction_failures.json`
- `output/paragraphs.json`
- `output/quote_lines.json`
- `output/quote_lines.txt`

Use `--output-mode both` to write PostgreSQL and all debug files.

## Bond Quote Console

The web console uses React, TypeScript, Ant Design Pro, and ProTable. It provides server-side pagination, filtering, and sorting for `ficc.bond_quote`, a separate extraction-failure view, and a JSON-backed evaluation annotation workspace. PostgreSQL credentials remain in the Python API and are never exposed to the browser.

Start the API from the project root:

```bash
python -m uvicorn ficc_bbg_parser.api:app \
  --host 127.0.0.1 \
  --port 8000 \
  --reload
```

Start the frontend development server in another terminal:

```bash
cd front
npm run dev
```

Open `http://127.0.0.1:5173/`. Vite proxies `/api` requests to `http://127.0.0.1:8000`, so no browser-side database configuration is required. FastAPI documentation is available at `http://127.0.0.1:8000/docs`.

The quote page supports keyword, ISIN, date range, currency, quote type, bond type, source, and parse-status filters. Click the eye button or double-click a row to inspect the complete quote, source paragraph, model metadata, and raw LLM payload. The extraction-failure page shows quote lines that were skipped after all retry attempts.

The evaluation annotation page is available at
`http://127.0.0.1:5173/#/annotation` in development or
`http://127.0.0.1:8000/#/annotation` after `front/dist` has been built.
It reads the source dataset and creates a separate working JSON on first save:

```dotenv
EVAL_DATASET_PATH=eval/eval_dataset.json
EVAL_ANNOTATED_PATH=eval/eval_annotated.json
```

Each save uses an atomic file replacement. The source evaluation dataset is
never modified. The page supports sample search/status filters, paragraph
context, current-prediction comparison, field availability, editable Gold
values, draft saves, completed-state validation, progress tracking, and JSON
download.

These paths are already covered by the repository `.gitignore`. A normal Git clone therefore contains only the frontend source and lock file. On a new server, `npm ci` recreates `node_modules`, and `npm run build` recreates `dist`.

To check exactly what Git will upload:

```bash
git status --short
```

### New Server Deployment

The simplest production layout is to build the frontend on the server and let FastAPI serve `front/dist`. In this mode the browser and API share one origin, PostgreSQL credentials remain on the server, and Node.js is not needed after the build finishes.

1. Clone the project and prepare Python:

```bash
git clone <repository-url> /opt/ficc_bbg
cd /opt/ficc_bbg

python3.9 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# Fill PostgreSQL, SQL Server, and LLM credentials in .env.
python -m ficc_bbg_parser.pg_schema
```

2. Verify Node.js and build the frontend:

```bash
node --version
npm --version

cd /opt/ficc_bbg/front
npm ci
npm run build
test -f dist/index.html
cd ..
```

3. Start the application after `front/dist` has been built:

```bash
cd /opt/ficc_bbg
source .venv/bin/activate
python -m uvicorn ficc_bbg_parser.api:app \
  --host 127.0.0.1 \
  --port 8000 \
  --workers 2
```

When `front/dist` exists before the API starts, FastAPI serves the compiled frontend at `http://127.0.0.1:8000/`. Build the frontend before starting Uvicorn; after rebuilding it, restart Uvicorn so deployment behavior stays predictable.

For a persistent Linux service, create `/etc/systemd/system/ficc-bbg.service`:

```ini
[Unit]
Description=FICC Bond Quote Console
After=network.target

[Service]
Type=simple
User=ficc
Group=ficc
WorkingDirectory=/opt/ficc_bbg
EnvironmentFile=/opt/ficc_bbg/.env
ExecStart=/opt/ficc_bbg/.venv/bin/python -m uvicorn ficc_bbg_parser.api:app --host 127.0.0.1 --port 8000 --workers 2
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Replace the service user and project path with the values used on the server, then enable it:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ficc-bbg
sudo systemctl status ficc-bbg
```

Put Nginx or another authenticated reverse proxy in front of Uvicorn. A minimal Nginx proxy is:

```nginx
server {
    listen 80;
    server_name your-internal-hostname;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

The current API does not implement user authentication. Keep it on a trusted internal network or configure authentication at the reverse proxy before exposing it to other networks.

## Evaluation Workflow

Evaluation code and generated files live in `eval/`. The files have different
roles and should be used in this order:

```text
PostgreSQL
  -> eval/eval_dataset.json    # frozen sample snapshot; annotation source only
  -> eval/eval_annotated.json  # reviewed Gold annotations; authoritative eval input
  -> eval/eval_inference.json  # predictions from the current extractor
  -> eval/eval_report.json     # metrics and field-level errors
```

### 1. Build the Frozen Sample Set

`eval_dataset.json` is created when a new evaluation set is sampled from
PostgreSQL. It preserves the original quote lines, paragraph context, source
metadata, and prediction snapshot used during initial screening. It is not the
Gold file and is not modified by the annotation page.

The initial 100-sample set uses a deterministic seed and the requested
`30/30/20/10/10` selection quotas:

```bash
python -m eval.build_eval_set \
  --output eval/eval_dataset.json \
  --seed 20260728 \
  --shortfall-policy backfill
```

Use `--shortfall-policy strict` when every difficulty bucket must be satisfied without replacement. Backfill mode retains each sample's real difficulty and records all quota substitutions in the JSON metadata. See `eval/README.md` for field definitions, manual annotation instructions, and tests.

Do not rerun this command merely to evaluate a new prompt or model. Rebuilding
the dataset may select different samples and make existing annotations
incompatible. Rebuild it only when intentionally creating a new evaluation-set
version, then annotate that version separately.

### 2. Create and Review Gold Annotations

When `eval_annotated.json` does not exist, the annotation page initializes from
`eval_dataset.json`. The first save creates `eval_annotated.json`; subsequent
annotation sessions read and update that working file directly. Once reviewed,
`eval_annotated.json` is the authoritative Gold input for evaluation, while
`eval_dataset.json` remains the unchanged source snapshot.

### 3. Run the Current Extractor

Run inference from the annotated Gold file into a separate prediction file.
Always pass `--input` and `--output` explicitly so the frozen source dataset is
not used accidentally:

```bash
python -m eval.run_inference \
  --input eval/eval_annotated.json \
  --output eval/eval_inference.json \
  --batch-size 10 \
  --workers 4
```

`run_inference` preserves every annotation and replaces only the prediction
snapshot in `eval_inference.json`.

### 4. Score the Predictions

Score the newly generated predictions against the Gold annotations carried
forward into `eval_inference.json`:

```bash
python -m eval.score_eval \
  --input eval/eval_inference.json \
  --output eval/eval_report.json \
  --strict-annotations
```

Do not score `eval_dataset.json` after annotation has started: it contains the
initial empty annotation fields rather than the reviewed Gold values. Use
`--strict-annotations` so incomplete or inconsistent completed annotations fail
fast instead of silently reducing evaluation coverage.

## Step-by-step Debugging

Run only the splitter from a debug txt file:

```bash
python -m ficc_bbg_parser.cli tests/email_text.txt --input-source txt --stage split --source-date 2026-06-04 --out-dir output
```

This writes `output/paragraphs.json`, `output/quote_lines.json`, and `output/quote_lines.txt`. The quote-line text file contains one quote statement per line. The splitter shows `LLM classify` progress by raw-message batch.

Run only LLM extraction from previously generated quote lines:

```bash
python -m ficc_bbg_parser.cli \
  --stage extract \
  --quote-lines-input output/quote_lines.json \
  --paragraphs-input output/paragraphs.json \
  --output-mode debug \
  --out-dir output \
  --extract-workers 4 \
  --batch-size 10
```

The extractor groups quote lines by paragraph and includes the first five lines of that paragraph once as auxiliary context in each LLM request. Paragraphs larger than `--batch-size` are split into multiple requests. Each batch gets three attempts by default. If all attempts fail because of request, response, JSON, or payload errors, the affected quote lines are recorded and skipped while later batches continue. The extractor shows quote and failure progress by default. Disable it with `--no-progress`.

## Production SQL Server Input

Production mode reads `CONTENT` from SQL Server for one `RECEIVE_DATE` day:

```bash
python -m ficc_bbg_parser.cli \
  --input-source sqlserver \
  --receive-date 2026-06-04 \
  --stage all \
  --output-mode postgres \
  --extract-workers 4
```

SQL Server settings live in `.env`:

```dotenv
DB_SERVER=172.30.10.78
DB_PORT=1433
DB_DATABASE=FICC_BBG_IB_PRD
DB_TABLE=BBG_IB_CHAT_EMAIL_INFO
DB_USERNAME=
DB_PASSWORD=
```

The SQL filter is:

```sql
WHERE RECEIVE_DATE >= @date AND RECEIVE_DATE < DATEADD(day, 1, @date)
```

### Full PostgreSQL Rerun

For development-time full reprocessing, use the range runner. It first queries
SQL Server for dates that actually contain non-empty email content, deletes old
`sqlserver` ingestion runs in the selected PostgreSQL date range, and then runs
the existing full pipeline once per source date:

```bash
python -m ficc_bbg_parser.rerun_full \
  --start-date 2026-06-01 \
  --end-date 2026-06-30
```

The date range is inclusive. The script asks for `YES` before deleting data;
use `--yes` for unattended development runs. By default it stops on the first
failed date and writes progress to
`output/full_rerun/rerun_summary.json`.

Preview SQL Server dates and generated commands without changing PostgreSQL:

```bash
python -m ficc_bbg_parser.rerun_full \
  --start-date 2026-06-01 \
  --end-date 2026-06-30 \
  --dry-run
```

To delete every ingestion run, including `txt` and manual debug runs, add
`--clear-scope all`. The default `--clear-scope range` deletes only
`source_mode=sqlserver` runs inside the selected dates.

If a date fails, fix the issue and resume without deleting completed dates:

```bash
python -m ficc_bbg_parser.rerun_full \
  --start-date 2026-06-18 \
  --end-date 2026-06-30 \
  --skip-clear
```

Use `--continue-on-error` to attempt later dates after a failure. Add
`--output-mode both` to retain per-date JSON/XLSX debug files beneath
`output/full_rerun/<date>/`; PostgreSQL-only output is the default.

## PostgreSQL Quote Store

### Fresh Environment Bootstrap

`pg_schema.py` creates and upgrades schemas, tables, indexes, and constraints. The PostgreSQL server, application role, and database must exist before running it.

For a new local Docker environment, create and start PostgreSQL 16:

```bash
docker run -d \
  --name pg_local \
  -e POSTGRES_PASSWORD=replace-with-admin-password \
  -p 5432:5432 \
  postgres:16
```

If the container already exists but is stopped:

```bash
docker start pg_local
```

Create the application login and database once, using the PostgreSQL administrator:

```bash
docker exec pg_local \
  psql -U postgres -d postgres \
  -c "CREATE ROLE ficc_app LOGIN PASSWORD 'replace-with-app-password';"

docker exec pg_local \
  psql -U postgres -d postgres \
  -c "CREATE DATABASE ficc_bbg OWNER ficc_app;"
```

If `ficc_app` already exists and only its password needs to be changed:

```bash
docker exec pg_local \
  psql -U postgres -d postgres \
  -c "ALTER ROLE ficc_app PASSWORD 'replace-with-app-password';"
```

Configure the same application credentials in `.env`:

```dotenv
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
POSTGRES_DATABASE=ficc_bbg
POSTGRES_SCHEMA=ficc
POSTGRES_USERNAME=ficc_app
POSTGRES_PASSWORD=replace-with-app-password
POSTGRES_SSLMODE=disable
```

Install dependencies and apply all migrations:

```bash
pip install -r requirements.txt
python -m ficc_bbg_parser.pg_schema
```

On a fresh database, the migration output should include the SQL files that were applied. Later runs are safe and should report `migrations=none` when the schema is current.

Verify the tables:

```bash
docker exec -e PGPASSWORD=replace-with-app-password pg_local \
  psql -h 127.0.0.1 -U ficc_app -d ficc_bbg \
  -c "\dt ficc.*"
```

The expected tables are `ingestion_run`, `chat_email`, `chat_paragraph`, `quote_line`, `bond_security`, `bond_quote`, `quote_extraction_failure`, and `schema_migration` in the `ficc` schema. Use strong administrator and application passwords outside local development.

The PostgreSQL schema follows the parser stages:

```text
ingestion_run
  -> chat_email
  -> chat_paragraph
  -> quote_line
       -> bond_quote
       -> quote_extraction_failure
```

`bond_security` stores enriched security-master data separately. `bond_quote` keeps typed query columns and the complete extractor result in `raw_payload JSONB`. Partial maturities such as `2031` and `2031-06` are stored using `maturity_text` and `maturity_precision`; `maturity_date` is used only when a full date is known.

Migrations are versioned and safe to run repeatedly. A source email is unique within an ingestion run, while `quote_sequence` allows defensive storage of more than one extracted quote from a malformed source line.

Each CLI write is transactional. If any database insert fails, the complete run is rolled back. Exhausted LLM retries do not stop the run: successful records go to `bond_quote`, while failed quote lines go to `quote_extraction_failure`. Successful output prints the PostgreSQL `run_id`, inserted quote count, and extraction failure count.

Check recent runs and quotes:

```sql
SELECT run_id, source_date, status, quote_count, completed_at
FROM ficc.ingestion_run
ORDER BY run_id DESC
LIMIT 20;

SELECT ticker, maturity_text, bid_price, ask_price,
       bid_spread, ask_spread, quote_time, quote_source
FROM ficc.bond_quote
ORDER BY quote_time DESC
LIMIT 50;

SELECT f.failure_id, f.model, f.attempts, f.error_type,
       f.error_message, l.line_id, l.text
FROM ficc.quote_extraction_failure f
JOIN ficc.quote_line l ON l.quote_line_pk = f.quote_line_pk
ORDER BY f.created_at DESC
LIMIT 50;
```

PostgreSQL settings live in `.env`:

```dotenv
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
POSTGRES_DATABASE=ficc_bbg
POSTGRES_SCHEMA=ficc
POSTGRES_USERNAME=ficc_app
POSTGRES_PASSWORD=
POSTGRES_SSLMODE=prefer
```

Useful tuning flags:

- `--batch-size`: maximum quote lines from one paragraph per extractor LLM call
- `--extract-workers`: number of parallel extractor LLM requests
- `--message-batch-max-chars`: target max payload chars per splitter LLM call
- `--model`: extraction model
- `--base-url`: OpenAI-compatible API base URL
- `--max-retries`: retries per LLM batch
- `--split-timeout`: HTTP timeout seconds for the splitter request
- `--extract-timeout`: HTTP timeout seconds for each extractor request
- `--output-mode postgres`: write PostgreSQL only; this is the default
- `--output-mode debug`: write JSON/XLSX and intermediate files only
- `--output-mode both`: write PostgreSQL and debug files

## Parsing Layers

1. Locally split raw Bloomberg chat text into timestamped raw messages using the Bloomberg time/speaker pattern.
2. Send raw message batches to the LLM classifier.
3. The classifier labels each message as `quote`, `axes`, `primary`, `stats`, `commentary`, or `noise`, and returns quote line ranges.
4. Local code slices the original text by line range into `quote_lines`, one bond quote per line.
5. The extractor groups quote lines by paragraph and receives the paragraph's first five lines once as auxiliary context plus the target quote lines.
6. The extractor returns structured quotes and records lines skipped after exhausted retries.
7. Store successful quotes and extraction failures with the complete source chain in one PostgreSQL transaction.
8. Optionally export JSON/XLSX, extraction failures, and intermediate files in `debug` or `both` mode.

Source metadata keeps people and institutions separate: `speaker` is the
Bloomberg sender/person parsed from the timestamp prefix, while `quote_source`
is only an institution or trading desk explicitly named in the message, such
as `SCB`, `SMBC`, or `ICBCI`. When no institution is stated, `quote_source` is
null; it never falls back to the speaker name.

## Notes

- ISIN, issuer full name, rating, currency, and region are only filled when the chat text or context provides them.
- A later security-master enrichment layer should match `ticker + coupon_rate + maturity_date + currency` or ISIN to fill missing static fields.
- Spread quotes store `bid_spread`, `ask_spread`, and `spread_bid_ask` in bp. Price quotes store `bid_price` and `ask_price`.
